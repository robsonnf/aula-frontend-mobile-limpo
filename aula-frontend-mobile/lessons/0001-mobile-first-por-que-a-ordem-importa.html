Mobile-first:
por que a ordem importa

Mobile-first não é “fazer o site funcionar no celular”. É uma ordem de escrita — e a ordem muda o código que sai. Hoje a turma vê a diferença nas duas folhas de estilo, lado a lado, e escolhe o tema do projeto que vai atravessar o semestre.

Roteiro — abertura (5 min)

Não começar por definição. Começar pela pergunta: “quantos de vocês desenharam um site pensando primeiro no celular?” Quase ninguém levanta a mão. Guardar essa resposta — ela volta no fechamento.

Aviso de formato: os 15 min iniciais de toda aula, a partir da A2, são recuperação ativa sem consulta. Hoje não tem — hoje é diagnóstico.

1. Comecemos pelo fato, não pela opinião

A indexação mobile-first do Google deixou de ser uma transição em 5 de julho de 2024, quando o rollout foi concluído. Desde então não existe mais exceção de rastreamento por desktop: o Google indexa e ranqueia a versão móvel do seu site, mesmo que seu usuário esteja num monitor de 27 polegadas.

A consequência prática

Se um conteúdo existe só na versão desktop, para efeito de busca ele não existe. Não é penalizado — simplesmente não é visto.

Google Search Central — Mobile-first indexing best practices

Roteiro — exposição 1 (40 min)

Ancorar em fato verificável antes de qualquer método. A turma chega achando que mobile-first é preferência estética de designer. Não é: é a condição de operação da web.

Se alguém perguntar “e se meu público é todo desktop?” — a resposta honesta é que isso muda a prioridade de teste, não a ordem de escrita. O motivo está na seção 3, não antecipar.

2. As duas direções

Existem exatamente duas maneiras de escrever CSS responsivo. Elas produzem a mesma tela e código profundamente diferente.

Desktop-down  ·  max-width

Escreve-se o layout largo primeiro. As media queries desfazem o que a base fez.

.cards {
  display: grid;
  grid-template-columns: repeat(3, 1fr);
  gap: 2rem;
  padding: 3rem;
}

@media (max-width: 48rem) {
  .cards {
    grid-template-columns: 1fr;  /* desfaz */
    gap: 1rem;                   /* desfaz */
    padding: 1rem;               /* desfaz */
  }
}

Mobile-up  ·  min-width

Escreve-se o layout estreito primeiro. As media queries só acrescentam.

.cards {
  display: grid;
  gap: 1rem;
  padding: 1rem;
}

@media (min-width: 48rem) {
  .cards {
    grid-template-columns: repeat(3, 1fr);
    gap: 2rem;
    padding: 3rem;
  }
}

Repare no que acontece com o celular em cada caso. Na folha da esquerda, o celular baixa a regra de três colunas, aplica, e depois baixa a regra que a cancela. Na da direita, o celular baixa a regra que serve a ele e para. A folha de base — a que todo dispositivo aplica, sem media query nenhuma — é a mais simples das duas.

Roteiro — demonstração

Colar as duas folhas no DevTools ao vivo e mostrar o painel Styles com a regra riscada. O risco na tela é o argumento — vale mais que a explicação.

Cuidado com a armadilha: alguém vai dizer “mas o navegador baixa o CSS inteiro de qualquer jeito”. Está certo. O ganho não é de download, é de cascata — menos regra sobreposta, menos especificidade acumulada, menos bug. Não vender mobile-first como otimização de rede; é honestidade que compra a confiança da turma.

3. Agora mexa você

Abaixo, a folha mobile-up rodando de verdade. O controle muda a largura do viewport, e as media queries disparam de fato — não é simulação.

Observe: arraste devagar até 768px. O rótulo muda no instante em que a media query passa a valer. Esse instante é o breakpoint — e repare que ele foi escolhido pelo conteúdo (é onde três cartões param de espremer), não porque algum celular tem essa largura.

O CSS abaixo está escrito desktop-down: a base tem três colunas e a media query desfaz. Reescreva mobile-up — base de uma coluna, min-width acrescentando. O resultado tem que ser idêntico nas duas pontas do controle. Conte as declarações antes e depois.

Conferência

A versão mobile-up tem três declarações a menos — as três que só existiam para cancelar a base. Não é economia de bytes: é uma regra a menos para depurar quando o layout quebrar em novembro.

Roteiro — prática 1 (30 min)

Tarefa: entregar a folha desktop-down e pedir que reescrevam mobile-up. Contar as declarações antes e depois. Sempre cai — e é a turma que descobre, não eu.

Quem terminar cedo: pedir para achar o breakpoint “errado” — um valor que corta uma palavra no meio. Serve de gancho para a A11.

4. Por que a ordem não é arbitrária

Três razões, em ordem crescente de importância:

Economia de cascata

Toda regra que desfaz outra é uma regra a mais para depurar. A folha mobile-up tende a ser menor porque não paga o imposto de cancelar a si mesma.

Orçamento por padrão

Escrever primeiro para a tela pequena obriga a decidir o que é essencial antes de decidir o que é enfeite. Restrição de espaço vira priorização de conteúdo — de graça.

A base é o piso, não a exceção

A folha sem media query é o que todo agente recebe: o celular antigo, o leitor de tela, o rastreador do Google, o navegador com CSS parcialmente carregado. Se essa base já é uma página utilizável, tudo que vem depois é melhoria. Se a base é um layout de três colunas quebrado, todo o resto é conserto.

Isso tem nome

Essa terceira razão é progressive enhancement — construir a partir de uma base que funciona e acrescentar capacidade conforme o ambiente permite. É o assunto inteiro da A3. Mobile-first é progressive enhancement aplicado a layout.

O min-width está em 20rem — cedo demais: os nomes quebram no meio. Arraste o controle até achar a largura em que os três cartões param de espremer, e ajuste o valor. O breakpoint sai do conteúdo, não de uma tabela de celulares.

5. A IA nesta disciplina

Você vai usar IA. Eu uso. O mercado usa. A regra da disciplina cabe em uma frase:

A regra

Use a IA à vontade. Você responde pelo que entrega, e vai defender oralmente.

Sem declaração obrigatória, sem detector, sem caça a plágio. Nada disso funciona, e eu não vou fingir que funciona.

O que muda é onde fica a nota. Os exercícios destas aulas não valem nota — são para você errar à vontade. A nota vive na defesa oral do seu projeto e numa modificação ao vivo, em aula, com a IA aberta se você quiser.

A razão é simples: a IA escreve o código por você, mas não senta na banca, não sabe por que o seu conteúdo pede aquele breakpoint, e não consegue modificar o que você não entendeu. Se você usou IA e consegue defender, modificar e diagnosticar — você aprendeu, e usou bem. É esse o objetivo.

Usar bem tem uma parte difícil

A parte difícil não é escrever o prompt. É revisar a resposta — porque nesta área específica a IA erra com confiança, repetindo conselho que era verdade em 2015. Alguns casos reais, verificáveis agora:

  • Sugerir jQuery Mobile, deprecado em 07/10/2021 e hoje projeto arquivado.
  • Dar WordPress 6.8 como versão atual quando a fonte oficial diz 7.1 (19/08/2026).
  • Mandar carregar codemirror do cdnjs na versão “6.65.7”, que é código da linha 5 — arquivada.

Nenhum desses é pegadinha. São o estado normal de uma ferramenta treinada em texto antigo. Sua defesa é a mesma que a de qualquer profissional: conferir na fonte primária. Por isso toda afirmação destas aulas vem com link para MDN, W3C ou a documentação oficial — não é enfeite acadêmico, é o hábito que estou tentando passar.

Pediram a uma IA: “deixa meu site responsivo”. Veio o CSS abaixo. Ele funciona — arraste o controle e veja. A pergunta não é se roda; é o que ele custa. Marque o que você acha que é problema. Nem tudo na lista é.

  1. A base, sem media query nenhuma, já é o layout de três colunas.
  2. Os breakpoints foram escolhidos por modelo de aparelho, não pelo conteúdo.
  3. Há declarações que existem só para cancelar outras declarações.
  4. Usar repeat(3, 1fr) em vez de larguras fixas em px.
  5. Usar gap em vez de margin entre os cartões.
Roteiro — a auditoria (20 min)

Deixe a turma marcar antes de comentar. Os dois decoys são o ponto da atividade: quase todo mundo marca pelo menos um. Aí a frase que fecha: “revisar IA não é desconfiar de tudo — é saber o que olhar.”

Se alguém perguntar “então o código da IA está certo ou errado?”: está funcionando e caro. Essa distinção é metade da disciplina.

Quem terminar cedo: peça para reescrever mobile-up e contar as declarações. Deve cair de 15 para 9.

Como você vai ser avaliado

Ao fim de cada fase do projeto, uma conversa de 10 minutos sobre o seu código, e uma modificação ao vivo que eu sorteio na hora. Duas perguntas que vão cair, para você já ir pensando:

  • “Você escolheu o breakpoint em tal medida. Por que não 10rem a mais? Me mostra na tela onde dói.”
  • “Apague a media query inteira agora. O que quebra?”

Se você fez mobile-first de verdade, a resposta da segunda é nada quebra no celular — só deixa de melhorar no desktop. É o teste mais rápido que existe, e vale para o seu projeto inteiro.

Tarefa de hoje — escolha do tema

Escolha um site real que você quer que exista: seu portfólio, o negócio de alguém da sua família, um coletivo, uma banda. Precisa ter conteúdo de verdade — texto e imagens que existem. Site de mentira não sobrevive a seis fases.
