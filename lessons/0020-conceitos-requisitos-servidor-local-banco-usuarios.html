CMS: servidor local,
banco e usuários

A home estática vira um sistema: navegador, servidor, PHP, banco, arquivos e pessoas com permissões diferentes. Nesta aula, cada camada recebe uma responsabilidade, uma evidência e um limite.

Ao final, você deverá montar um ambiente WordPress local, distinguir banco de arquivos, aplicar menor privilégio e registrar uma base restaurável para a F5.

Versão, laboratório e limite

Referência conferida em 07/10/2026: WordPress 7.1.3, versão de manutenção e segurança publicada em 06/10/2026. A rota principal do laboratório é WordPress Studio. Ele usa SQLite por padrão; produção deve ser validada contra os requisitos reais do host. As prévias desta aula simulam contratos e funcionam offline: elas não executam PHP nem substituem uma instalação WordPress.

Copiar apenas a pasta do WordPress produz um backup completo?

  • Sim, porque o banco fica dentro de wp-content
  • Não; banco e arquivos formam o conjunto restaurável
  • Sim, se o tema filho estiver ativo

1. CMS não é apenas um editor

Um CMS administra conteúdo, apresentação, extensões e acesso. No WordPress, o navegador solicita uma URL; o servidor encaminha a execução; PHP e o core consultam configuração, conteúdo, tema e plug-ins; o banco devolve dados; a resposta HTML volta ao navegador. Cache pode atender parte do percurso, mas não elimina as camadas.

No DevTools — seção 1

Network mostra a requisição do documento e seus recursos, não a consulta SQL interna. Abra Headers, Response e Timing. A prévia é uma simulação estática: para observar PHP e banco, combine Network com logs do servidor e Site Health na instalação local.

2. Requisitos: recomendado não é o mesmo que legado tolerado

Na data desta revisão, o WordPress recomenda PHP 8.3+, MariaDB 10.11+ ou MySQL 8.0+ e HTTPS. A página oficial ainda descreve versões antigas que podem executar o sistema, mas já chegaram ao fim de vida; “funcionou” não as torna base segura. Apache ou Nginx são recomendados, embora qualquer servidor compatível possa atender.

No DevTools — seção 2

Network → documento confirma protocolo, status e cabeçalhos públicos. Security confirma a conexão HTTPS quando publicada. A versão do banco não deve ser deduzida do HTML; confira Site Health ou o painel autorizado do host.

3. Servidor local adotado: WordPress Studio

Studio cria e inicia sites locais em Windows, macOS e Linux compatível. Em Add site, escolha um site vazio, versão estável e credenciais próprias; depois use Open Site e WP Admin. O local serve para desenvolver e testar sem alterar produção. Por padrão, Studio guarda o banco em SQLite e oferece uma interface phpMyAdmin adaptada.

Alternativa para equipe com Docker: wp-env é mantido pela comunidade de desenvolvimento do WordPress, mas exige Node e Docker. XAMPP, Local, MAMP e outros continuam opções; a aula padroniza Studio para reduzir diferenças operacionais. Nenhuma credencial real deve entrar em screenshot ou repositório.

No DevTools — seção 3

No site iniciado, Network → documento confirma a URL local e o servidor em execução. Application → Cookies mostra a sessão após login; não copie valores. Studio → Overview abre phpMyAdmin; Studio → Settings mostra versões e permite ativar debug log.

4. Exercício: relatório de prontidão sem segredos

Repare o relatório: use estrutura de dados adequada, registre versões e finalidade do ambiente, identifique a divergência SQLite × produção e remova credenciais. Não declare HTTPS ou compatibilidade que ainda não foi verificada.

Separe evidência, pendência e segredo. Pergunte de qual painel cada valor veio e se ele descreve o local ou o servidor de publicação.

No DevTools — seção 4

Elements verifica heading, dl/dt/dd e ausência de segredo. Accessibility confirma a estrutura textual. Network não comprova valores escritos manualmente: anote junto a cada versão a origem no Studio, Site Health ou painel do host.

5. Banco e arquivos: duas metades do mesmo site

Posts, páginas, opções, usuários e relações ficam no banco. Core, temas, plug-ins e uploads ficam em arquivos, embora extensões possam criar dados próprios. Um backup restaurável normalmente inclui os dois, produzidos como um conjunto consistente. Exportar conteúdo pelo painel não equivale necessariamente a copiar o site inteiro.

No DevTools — seção 5

Network → Img revela o arquivo transferido, não o registro que o referencia. Application não é o banco do WordPress. No Studio, abra phpMyAdmin para consultar tabelas sem editar diretamente o arquivo SQLite; em Files, localize wp-content.

6. Usuários: papel reúne capacidades

WordPress possui Administrator, Editor, Author, Contributor e Subscriber em um site simples; Super Admin pertence ao contexto Multisite. Papéis agrupam capacidades. Conceda a menor permissão que conclui a tarefa: quem revisa e publica conteúdo de outras pessoas pode ser Editor, sem instalar plug-ins nem alterar usuários.

No DevTools — seção 6

Elements mostra controles e status desta simulação. No WordPress, compare menus com duas contas de teste e use Network para observar 403 em ação não autorizada. Esconder um botão com CSS não remove a capacidade no servidor.

7. Exercício: aplique menor privilégio

Corrija pode(): Editor publica conteúdo da equipe; Author publica apenas o próprio; Administrator instala plug-ins; Subscriber apenas lê. Trocar o papel deve atualizar a resposta. Não use uma regra “qualquer usuário logado”.

Modele as capacidades necessárias para cada tarefa e compare conjuntos. Teste todas as combinações, inclusive uma ação negada.

No DevTools — seção 7

Sources pausa em pode() e inspeciona papel/tarefa. Teste Subscriber × instalar e Editor × equipe. Na aplicação real, a resposta do servidor é decisiva: interface oculta sem verificação de capacidade continua insegura.

8. Auditoria: painel local responsivo e operação segura

Requisitos: operar o painel em 320px por teclado, manter avisos visíveis, aplicar menor privilégio e preparar backup restaurável. Audite CSS e decisões da equipe; repare no editor os problemas de apresentação.

Meça a caixa, navegue com Tab e liste o que pertence ao servidor. Uma propriedade CSS não revela banco por magia; uma interface bonita não corrige papel excessivo nem backup incompleto.

  1. overflow-x:auto na tabela é sempre falha de responsividade.
  2. main impede o reflow da página.
  3. Usar CSS customizado revela automaticamente as credenciais do banco.
  4. O CSS remove o aviso de banco não validado.
  5. O indicador de foco foi eliminado.
  6. Todo ambiente WordPress local é obrigado a executar MySQL.
  7. Os dois usuários receberam privilégio excessivo.
  8. Falta criar um Super Admin para o site simples funcionar.
  9. A decisão de guardar somente o banco produz backup incompleto.
No DevTools — seção 8

Device Toolbar em 320px mostra o overflow da página; Elements/Computed confirma display e width; Tab revela foco. Network e CSS não comprovam backup ou papel: valide esses itens no painel, nos arquivos e em um teste de restauração.

Qual papel padrão atende quem publica conteúdo de toda a equipe?

  • Subscriber
  • Editor
  • Administrator obrigatoriamente

9. Entrega F5 — parte 1: base local reproduzível

  1. Crie um site vazio no Studio e registre WordPress/PHP/local URL.
  2. Crie páginas equivalentes às regiões da home e uma navegação funcional.
  3. Crie contas de teste com Editor e Author; mantenha um Administrator separado.
  4. Registre banco local, banco previsto no host e diferenças conhecidas.
  5. Exporte um backup completo e anote como restaurá-lo; não entregue credenciais.

Adicione CMS.md ao projeto com ambiente, versões, mapa de conteúdo, papéis, conjunto de backup e pendências. A A21 usará essa base para tema filho, plug-ins e publicação.

No DevTools — seção 9

Network registra home, wp-admin e respostas de ações permitidas/negadas. Application confirma que cada conta usa sessão distinta sem copiar cookies. Site Health e Studio fornecem versões. Anexe evidências sem nomes, e-mails ou tokens reais.
