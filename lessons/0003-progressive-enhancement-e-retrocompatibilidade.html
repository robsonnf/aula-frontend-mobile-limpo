Progressive enhancement
e retrocompatibilidade

Compatibilidade não é fazer tudo parecer igual em todo navegador. É garantir um piso útil e acrescentar recursos quando a plataforma consegue sustentá-los. Hoje a turma constrói esse piso, usa @supports e aprende quando um prefixo é evidência — e quando é só arqueologia copiada.

Qual afirmação sobre a meta viewport está correta?

  • Ela transforma qualquer largura fixa em layout responsivo.
  • Ela configura o viewport; não corrige o layout por conta própria.
  • Ela deve bloquear o zoom para impedir quebra visual.

1. Primeiro, o que não pode falhar

Progressive enhancement é uma filosofia de projeto: entregar conteúdo e funcionalidade essenciais ao maior número possível de pessoas, e oferecer uma experiência mais rica quando o navegador consegue executar as camadas adicionais.

A pergunta que vem antes da tecnologia

Qual é a tarefa essencial desta página? Comprar, ler, enviar, encontrar um endereço? Essa tarefa precisa existir no piso. Animação, grade sofisticada e conveniência entram depois.

MDN — Progressive enhancement

Começa pelo teto

Constrói a experiência completa e tenta consertar o que quebrou em agentes menos capazes. O fallback nasce como remendo.

Começa pelo piso

HTML entrega conteúdo e ação; CSS melhora apresentação; JavaScript acrescenta comportamento. Cada camada encontra algo útil abaixo dela.

2. Três camadas, três responsabilidades

CamadaPiso que entregaExemplo
HTMLConteúdo, controles e destino reaisUm link continua navegando sem script.
CSSApresentação com fallback pela cascataBlocos empilhados viram grid quando há suporte.
JavaScriptConveniência e comportamento adicionalFormulário envia normalmente e ganha validação imediata.
 
.aviso {
  background: #eee;                /* piso */
  background: color-mix(in srgb, #fff 82%, #9c2f22); /* melhoria */
}

CSS foi desenhado para recuperação de erros: uma declaração com propriedade ou valor inválido é ignorada, sem invalidar necessariamente a regra inteira. Por isso o fallback vem primeiro e a melhoria depois. O navegador antigo conserva o valor que entendeu; o novo substitui pela declaração posterior.

3. Detecte a capacidade, não adivinhe o navegador

@supports aplica um bloco somente quando o navegador declara suporte à condição testada. É feature detection: perguntar “você entende isto?” em vez de inferir capacidade por nome e versão do agente.

.galeria { display: flex; flex-wrap: wrap; }

@supports (display: grid) {
  .galeria {
    display: grid;
    grid-template-columns: repeat(3, 1fr);
  }
}

@supports testa se a sintaxe é reconhecida; não prova ausência de bugs, qualidade da implementação nem adequação ao projeto. Ainda é preciso testar.

MDN — @supports

O layout começa escondendo os cartões e só os mostra dentro de @supports. Inverta a dependência: crie um piso em bloco ou flex que sempre funcione e use a feature query apenas para acrescentar Grid. Preserve conteúdo, ordem e espaçamento.

4. Baseline é um sinal, não uma promessa universal

Baseline resume a interoperabilidade de recursos da plataforma nos navegadores principais. Newly available indica que o recurso passou a ser suportado no conjunto principal; Widely available significa que se passaram pelo menos 30 meses desde esse marco.

O que Baseline não sabe

Ele não conhece os navegadores reais do seu público, webviews antigas, política de atualização da empresa nem o custo de perder a funcionalidade. “Widely available” reduz incerteza; não substitui requisito e teste.

MDN — Baseline (compatibility)

SituaçãoDecisão razoável
Recurso amplamente disponível e melhoria visualUsar; manter um piso simples quando for barato.
Recurso recente e tarefa essencialMedir público, testar e oferecer alternativa real.
Navegador corporativo impostoTransformar a versão mínima em requisito explícito.
“Funciona no meu Chrome”Ainda não é evidência de compatibilidade.

5. Prefixo não é amuleto

Prefixos como -webkit-, -moz- e -ms- registram fases experimentais ou implementações específicas. Copiar todos para toda propriedade não cria compatibilidade. Pode apenas preservar sintaxe antiga que nenhum alvo precisa.

Folclore manual

-webkit-border-radius: 8px;
-moz-border-radius: 8px;
border-radius: 8px;

Não há alvo declarado nem dado que justifique as duas primeiras linhas.

Decisão rastreável

border-radius: 8px;

Consulte compatibilidade. Se o projeto exigir transformação, gere-a a partir da lista de navegadores-alvo e teste o resultado.

Autoprefixer usa dados do Can I Use e uma lista de navegadores-alvo para adicionar prefixos necessários. Ele não é polyfill e não transforma qualquer recurso moderno em equivalente antigo. Neste curso não instalaremos build só para uma linha; o princípio é separar CSS-fonte legível de compatibilidade gerada quando o projeto pedir.

Qual é a estratégia mais defensável?

  • Adicionar todos os prefixos conhecidos a toda propriedade CSS.
  • Detectar Safari pelo texto do user agent e criar uma folha separada.
  • Definir o piso, consultar suporte e testar os navegadores-alvo.

6. Audite CSS plausível, mas caro

Pediram: “faça estes cartões funcionarem em navegadores antigos”. O resultado parece cuidadoso. Marque somente problemas reais. Há escolhas corretas e decoys.

  1. O bloco @supports not esconde todo o conteúdo quando Grid não existe.
  2. A regra .safari tenta inferir comportamento pelo navegador.
  3. Os prefixos de border-radius foram adicionados sem requisito ou dado de suporte.
  4. Declarar color duas vezes, com o valor literal antes de var().
  5. Usar Flex no piso e Grid dentro de @supports.

7. Aplique ao Projeto UC15 - HTML Mobile first

Pegue o esqueleto semântico da A2. Sua tarefa não é fazê-lo bonito ainda; é registrar o contrato de funcionamento antes das aulas de CSS:

  1. circule o conteúdo e as ações que precisam funcionar no piso;
  2. marque cada melhoria desejada como apresentação ou comportamento;
  3. para uma melhoria recente, registre fonte de compatibilidade e fallback;
  4. desative JavaScript e confirme que conteúdo e navegação essenciais sobrevivem;
  5. não adicione prefixo sem navegador-alvo que o justifique.

O destaque depende de color-mix(). Acrescente antes dele um fundo literal coerente. Depois envolva apenas a melhoria em @supports. Se a melhoria desaparecer, texto e contraste ainda precisam funcionar.

Entrega da A3

Junto do index.html, entregue COMPATIBILIDADE.md com três linhas: tarefa essencial, melhoria escolhida e fallback. Inclua o link da fonte usada para decidir suporte. Curto o bastante para continuar verdadeiro.

Leitura primária

Leia MDN — Progressive enhancement e MDN — Baseline compatibility. Depois abra a página MDN de uma propriedade que você quer usar e procure o selo Baseline e a tabela de compatibilidade. O selo inicia a pergunta; seu público termina a resposta.

Ficou alguma coisa mal explicada? Traga o caso e o navegador-alvo. “Preciso suportar navegador antigo” só vira requisito quando “antigo” ganha nome, versão, público e consequência.
