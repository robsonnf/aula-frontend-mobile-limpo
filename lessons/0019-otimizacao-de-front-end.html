Otimização
de front-end

Otimizar é medir uma tarefa, localizar seu gargalo e comparar uma mudança sob condições controladas. Vamos trabalhar carregamento, renderização, responsividade e estabilidade sem trocar experiência real por uma pontuação isolada.

Ao final, você deverá interpretar Core Web Vitals, ler waterfall e main thread, reparar imagens e JavaScript e documentar ganhos com contexto e limites.

Laboratório, campo e DevTools

Dados de laboratório são reproduzíveis e úteis para diagnóstico; dados de campo representam usuários reais agregados. Eles podem divergir por dispositivo, rede, cache e interação. Use Network, Performance e Lighthouse no mesmo perfil de teste, mas não apresente uma execução local como experiência de todos os usuários.

Por que laboratório e campo podem mostrar resultados diferentes?

  • Porque apenas o laboratório mede JavaScript
  • Porque usam populações e condições de coleta diferentes
  • Porque dados de campo não incluem dispositivos móveis

1. Métricas centradas na experiência

Os Core Web Vitals atuais avaliam carregamento com LCP, responsividade com INP e estabilidade visual com CLS. Para classificar como “bom”, as referências são LCP até 2,5 s, INP até 200 ms e CLS até 0,1, avaliadas no percentil 75 das visitas. Métrica indica sintoma; a investigação encontra elemento, tarefa e causa.

MétricaPerguntaBom
LCPQuando o maior conteúdo visível aparece?≤ 2,5 s
INPComo a página responde às interações?≤ 200 ms
CLSQuanto o conteúdo muda inesperadamente?≤ 0,1
No DevTools — seção 1

Performance → Record and reload mostra marcadores e trilhas de Web Vitals. Lighthouse fornece laboratório; PageSpeed Insights pode combinar laboratório e campo quando há dados suficientes. Registre origem, data, dispositivo e condição junto a cada número.

2. Waterfall: solicitação, transferência e cache

O waterfall revela dependências, bloqueios e ordem. Transferred pode incluir compressão e cache; resource size representa tamanho decodificado. Headers como cache-control e content-encoding pertencem à resposta HTTP. Um arquivo pequeno pode chegar tarde por cadeia de dependências, latência ou prioridade inadequada.

No DevTools — seção 2

Network: marque Disable cache somente para a carga fria, escolha Fast 4G e recarregue. Mostre Waterfall, Initiator, Size e Timing. Depois desmarque Disable cache e compare a carga repetida. Anote as condições; não misture os dois cenários.

3. Caminho crítico, CSS e JavaScript

CSS pode bloquear a primeira renderização; scripts clássicos sem defer podem bloquear o parser. defer preserva ordem entre scripts defer e executa após o parse; módulos são adiados por padrão. Dividir código só ajuda quando reduz trabalho necessário na rota e não cria excesso de solicitações. Minificar reduz texto, mas não elimina execução, dependências ou lógica desnecessária.

No DevTools — seção 3

Sources localiza o script; Performance grava a carga e depois o clique. Na Main, expanda tarefas e use Bottom-up para atribuir tempo. Coverage aponta bytes não usados nesta navegação, mas não prova que sejam desnecessários em todas as rotas.

4. Exercício: impedir deslocamento e priorizar a hero

Dimensões intrínsecas ou aspect-ratio reservam espaço antes da imagem e ajudam a evitar CLS. Imagens abaixo da dobra podem usar lazy loading nativo; a imagem LCP visível inicialmente não deve ser atrasada com loading="lazy". Use fetchpriority="high" com parcimônia, apenas para um recurso realmente prioritário.

Repare a imagem principal: reserve sua proporção antes do download, não a carregue de forma preguiçosa e forneça candidatos responsivos com sizes coerente para um slot de até 720px.

Identifique se a imagem está no viewport inicial. Depois separe três decisões: quando descobrir, qual candidato baixar e quanto espaço reservar.

No DevTools — seção 4

Network → Img mostra prioridade, iniciador e recurso escolhido; Console consulta document.querySelector('img').currentSrc. Performance → Experience localiza layout shifts. Teste sem cache e não atribua bytes reais aos candidatos SVG repetidos da demonstração.

5. Exercício: reduzir trabalho por interação

INP inclui atraso de entrada, processamento e apresentação do próximo frame. Um handler deve fazer o trabalho necessário sem forçar leituras e escritas de layout em ciclo. Delegação reduz listeners em listas dinâmicas, mas não torna processamento pesado automaticamente rápido. Meça a tarefa específica antes e depois.

Repare a seleção: use um listener delegado na lista, altere somente o botão acionado e atualize a contagem uma vez. Deve funcionar também para um item inserido depois e para clique no span interno.

Observe quantos listeners foram instalados, qual elemento é target e onde procurar o botão correspondente. Evite percorrer e reescrever todos os itens quando apenas um mudou.

No DevTools — seção 5

Elements → Event Listeners compara listeners antes/depois de criar itens. Performance grava clique e inserção; Sources usa breakpoint no handler e observa target/closest. Não use uma diferença minúscula desta amostra como promessa de ganho em produção.

6. Fontes, renderização e estabilidade

Fontes web acrescentam requisições e podem trocar métricas do texto. Subconjuntos, formatos adequados, preload criterioso e font-display fazem parte da decisão, mas cada estratégia tem trade-offs. Fallbacks com métricas muito diferentes podem deslocar conteúdo. Não esconda texto indefinidamente à espera de uma fonte.

No DevTools — seção 6

Elements → Computed → Rendered Fonts mostra a fonte usada em cada trecho. Network filtra Font; Rendering pode destacar layout shift regions. A demonstração usa fonte do sistema de propósito: ausência de download também é uma decisão de desempenho.

7. Orçamento, hipótese e comparação justa

Um orçamento define limites por tipo e rota: bytes transferidos, quantidade de recursos, trabalho de JavaScript ou métricas de experiência. Ele deve nascer de público e produto, não de número universal. Compare o mesmo fluxo, em perfil equivalente, com várias execuções e mediana; documente variação, regressões e custo de manutenção.

No DevTools — seção 7

Crie um Performance trace antes e outro depois com a mesma configuração. Em Network, exporte HAR sem dados sensíveis se precisar comparar waterfall. Lighthouse permite configurar modo e dispositivo; guarde configurações junto aos resultados.

8. Auditoria: home rápida no papel, lenta na tarefa

Requisitos: hero estável e prioritária, conteúdo abaixo da dobra adiado, foco preservado e animação econômica. Audite HTML e CSS; repare no CSS o que puder e registre quais correções pertencem ao HTML ou servidor.

Separe rede, layout, pintura e interação. Desligue propriedades uma a uma e procure a métrica afetada. Nem toda prática com nome de performance é adequada em todos os elementos.

  1. A imagem principal não deveria usar lazy loading neste cenário.
  2. max-width:100% faz o navegador baixar duas imagens.
  3. A hero não reserva espaço antes do carregamento.
  4. content-visibility:auto é sempre pior para desempenho.
  5. will-change global é uma otimização contraproducente.
  6. O foco visível foi eliminado.
  7. Qualquer transform aciona obrigatoriamente layout completo.
  8. A animação não cobre teclado nem movimento reduzido.
  9. A ausência da palavra gzip no CSS prova que o servidor não comprime arquivos.
No DevTools — seção 8

Network confirma loading/prioridade e headers; Performance → Experience mostra shifts; Layers/Rendering ajuda a investigar pintura; Computed verifica foco e will-change. Classifique cinco problemas reais e quatro decoys sem atribuir ao CSS o que só a resposta HTTP pode provar.

Qual imagem é a pior candidata a loading="lazy"?

  • Uma miniatura muito abaixo da dobra
  • A hero visível inicialmente e provável LCP
  • Uma imagem aberta somente numa rota futura

9. Entrega da F4: relatório de qualidade e plano

  1. Escolha três tarefas: carregar, interagir e navegar na home.
  2. Fixe viewport, CPU/rede, cache e versão do navegador.
  3. Registre LCP/INP ou proxy de laboratório/CLS e waterfall antes.
  4. Implemente uma correção por causa demonstrada e repita as medições.
  5. Atualize QUALIDADE.md com mediana, variação, regressões e próximo passo.

Combine o relatório com A17 e A18: uma otimização não pode remover nome, foco, conteúdo mobile ou link rastreável. Entregue evidência, não apenas a nota do Lighthouse.

No DevTools — seção 9

Guarde screenshots ou traces de Network/Performance e a configuração. Compare três ou mais execuções quando possível. Em Lighthouse, leia cada oportunidade e valide a causa no painel correspondente antes de transformar a sugestão em tarefa.
