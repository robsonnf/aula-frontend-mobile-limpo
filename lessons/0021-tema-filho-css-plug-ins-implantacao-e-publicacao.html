Tema filho, plug-ins
e publicação

Publicar não é copiar uma aparência: é tornar customizações atualizáveis, escolher extensões por requisito e mover arquivos e banco com retorno planejado. A F5 termina no ar sem abandonar acessibilidade, SEO ou desempenho.

Ao final, você deverá criar um tema filho reconhecível, aplicar CSS com escopo, justificar plug-ins, implantar em staging/produção e executar um smoke test com rollback.

Escopo e segurança operacional

A aula usa WordPress 7.1.3 como referência conferida em 07/10/2026. Não faça a primeira tentativa em produção. Antes de tema, plug-in, atualização ou migração, mantenha backup restaurável de arquivos e banco. As prévias locais demonstram HTML, CSS e JS; PHP, hooks e publicação devem ser testados no site WordPress da A20.

Onde deve ficar uma funcionalidade que precisa sobreviver à troca de tema?

  • No CSS do tema pai
  • Em um plug-in adequado ou no core
  • Em um comentário dentro de theme.json

1. Linha de base antes da customização

Confirme versão, tema pai, conteúdo, URLs, papéis e backup da A20. Faça uma captura da home em 320px e desktop, teste teclado e registre Network/Lighthouse como referência. Uma mudança só é melhoria se a tarefa continua funcionando e o efeito pode ser revertido.

No DevTools — seção 1

Preserve um trace ou HAR sem dados sensíveis e capturas de Elements/Accessibility. Use o mesmo viewport, navegador e cache nas comparações. DevTools produz evidência da interface; backup e rollback são comprovados fora dele.

2. Tema filho: herdar sem editar o pai

O tema filho herda o pai e mantém customizações separadas para que o pai possa ser atualizado. O arquivo mínimo para o WordPress reconhecer o filho é style.css com cabeçalho; Template deve corresponder exatamente à pasta do tema pai. O pai precisa estar instalado. functions.php do filho é carregado além do arquivo do pai — ele não o substitui.

/*
Theme Name: F5 Child
Template: twentytwentysix
Version: 1.0.0
Text Domain: f5-child
*/

Temas de blocos usam principalmente HTML e theme.json; temas clássicos usam PHP, hooks e templates tradicionais. Um tema filho pode sobrescrever templates, parts e patterns conforme o tipo do pai. Não copie o tema inteiro sem necessidade.

No DevTools — seção 2

Elements → body mostra classes de tema/contexto. Network → CSS revela a URL em wp-content/themes/f5-child/, status e ordem de carga. Sources confirma qual arquivo entregou a regra; o nome visual no painel não prova sozinho o Template correto.

3. CSS, theme.json e fila de assets

Em tema de blocos, prefira theme.json para propriedades suportadas: o Site Editor entende tokens e estilos sem guerra de especificidade. CSS continua válido para o que não cabe ali. Em temas clássicos e folhas adicionais, use wp_enqueue_style() no hook wp_enqueue_scripts; não cole links fixos no head. Versão do asset ajuda a invalidar cache.

<?php
add_action( 'wp_enqueue_scripts', 'f5_child_styles' );
function f5_child_styles() {
    wp_enqueue_style(
        'f5-child',
        get_stylesheet_uri(),
        array(),
        wp_get_theme()->get( 'Version' )
    );
}
No DevTools — seção 3

Elements → Styles identifica seletor, origem e regra sobrescrita. Computed mostra o valor final e a variável usada. Network → CSS confirma handle/URL/versão; Disable cache serve ao diagnóstico local, não substitui versionar corretamente o asset.

4. Exercício: CSS do filho sem efeito colateral

Repare o CSS: limite a customização ao bloco da F5, remova força desnecessária, mantenha foco visível, permita quebra do grupo e não esconda a descrição no mobile. O link principal deve continuar identificável sem depender de hover.

Localize quem ganha na cascata e qual ancestral oferece escopo. Teste 320px, teclado e texto ampliado. Não aumente especificidade antes de entender a origem.

No DevTools — seção 4

Styles mostra o fim de !important e o escopo .site-f5. Computed confirma max-width, flex-wrap, cor e outline. Device Toolbar em 320px e Tab verificam reflow/estados; use Coverage apenas para a rota observada, sem declarar o restante do CSS inútil.

5. Plug-in: requisito, procedência e ciclo de vida

Plug-in estende funcionalidade. Antes de instalar, escreva o requisito e verifique procedência, versão compatível, manutenção, suporte, licença, acessibilidade, dados criados, impacto, desinstalação e alternativa do core. Quantidade de instalações ou avaliação alta não substitui esse conjunto. Teste no local/staging e faça backup antes de atualizar. Extensão inativa e sem uso deve ser removida, não colecionada.

No DevTools — seção 5

Network compara recursos antes/depois; Coverage e Performance ajudam a localizar custo na rota. Application revela cookies/storage adicionados. Console mostra erros, mas ausência de erro não comprova segurança, privacidade ou compatibilidade.

6. Exercício: decisão baseada em evidência

Corrija avaliar(): o candidato só pode ser aprovado quando requisito, fonte, compatibilidade, dados e rollback estiverem verificados. Atualize o status a cada mudança e liste quantos bloqueadores faltam.

Leia os checkboxes como condições necessárias, não como pontos. Teste zero, um e todos marcados. Uma popularidade alta não aparece porque não substitui os critérios.

No DevTools — seção 6

Sources pausa em avaliar() e inspeciona faltam. Elements → Accessibility confirma fieldset/legend e estados checked. No site real, Network/Performance fornece parte da ficha; changelog, licença, dados e rollback exigem documentação e teste externo.

7. Implantar é mover um sistema, não só HTML

A sequência segura é: staging compatível; backup conjunto e restauração conhecida; arquivos e banco; URLs migradas com ferramenta consciente de dados serializados; configuração/segredos do destino; HTTPS e permalinks; smoke tests; monitoramento e rollback. Um replace bruto no SQL pode corromper valores serializados.

Studio exporta site completo ou banco; formatos e recursos do host determinam a restauração. Studio Sync serve apenas a destinos compatíveis e pode substituir banco: revise o escopo. Qualquer fluxo automático continua exigindo backup e teste.

No DevTools — seção 7

Network confirma redirects, HTTPS, status, canonical e recursos sem 404. Application verifica cookies e cache do novo domínio; Console procura erros. Preserve o log do host e Site Health para falhas PHP. Um 200 na home não conclui o smoke test.

8. Auditoria: front-end do tema e plano de publicação

Requisitos: home utilizável em 320px/teclado, aviso de atualização visível e customização isolada no filho. O plano deve preservar update, dados e rollback. Audite CSS e decisões; repare os problemas visuais no editor.

Localize a origem da regra antes de aumentar sua força. Separe o que Styles resolve do que exige tema, plug-in, banco ou host. Decoy plausível ainda precisa de evidência para ser rejeitado.

  1. A equipe alterou diretamente o CSS do tema pai.
  2. O campo Template usar o nome da pasta do pai é um erro.
  3. A home não reflui no viewport estreito.
  4. O aviso de atualização foi escondido pelo CSS.
  5. Todo CSS do filho deve ser inserido com uma tag link escrita manualmente.
  6. O plano usa localizar/substituir textual direto em todo o SQL para trocar domínio.
  7. Usar theme.json impede qualquer CSS adicional.
  8. Foco e ações deixam de funcionar bem por teclado/viewport estreito.
  9. O rollback guarda somente o banco.
No DevTools — seção 8

Device Toolbar, Styles e Computed revelam largura, display, !important, flex e outline. Network confirma a folha do filho e 404; não valida search-replace ou backup. São seis problemas reais e três decoys: discuta o texto, pois a ordem muda.

Qual vantagem central do tema filho?

  • Separar customização do código atualizável do pai
  • Eliminar a necessidade de tema pai instalado
  • Transformar todo plug-in em CSS

9. Entrega F5 — parte 2: publicar com retorno

  1. Crie/ative o tema filho e versione seus arquivos próprios.
  2. Transfira a home preservando HTML semântico, responsividade e estados.
  3. Para cada plug-in, complete requisito, procedência, dados, custo e rollback.
  4. Implante primeiro em staging compatível; execute A17, A18 e A19 novamente.
  5. Faça backup de produção, publique, rode smoke test e monitore; reverta se falhar.

Atualize CMS.md com tema pai/filho, arquivos, plug-ins/versões, migração, URLs, teste, backup e retorno. Não inclua senha, chave, cookie, dado pessoal ou dump no Git.

No DevTools — seção 9

Network: documento, CSS do filho, assets, redirects e status. Elements/Accessibility: semântica/foco. Lighthouse e Performance: regressões. Application: cookies/cache do domínio certo. Repita anônimo e autenticado com contas de teste separadas.
